# Iteration 206 — profile the links command's 12.7s GitHub Docs run

## Goal

Profile and address the `links` command's ~12.7s runtime observed against
the GitHub Docs corpus during the v0.21.0-pre dogfood. This was flagged as
a non-goal / "profile separately" item in both
[[iteration-200-links-apply-integrity]] and
[[iteration-203-index-md-resolution]] and never got its own plan — this
iteration is that plan.

## Context

Carried over from iteration 200's Non-goals section:

> The `links` 12.7s perf issue on GitHub Docs — profile separately.

No repro numbers or profiling data were captured beyond the headline
figure at dogfood time. First task here is therefore to reproduce and
measure before proposing a fix — do not assume the cause.

Corroborating data point from iter-203's MDN measurement run (14,375
files, read-only): `links` still took ~80s there too, unchanged by
iter-203's directory-index resolution — so the cost is orthogonal to
that change and reproduces on a second, larger corpus.

**Rescoped by the 2026-08-23 dogfood**
([[dogfood-results/dogfood-v0210-pre2-integrity-wave]], Performance):
the ~80s MDN figure occurs only *without* a site prefix, where all
49,703 links are broken and each pays the fuzzy-candidate cost; with
`--site-prefix "en-US/docs"` (509 broken) the same command takes 8.7s,
and 5.5s with a matching snapshot index. GitHub Docs measured 11.6s vs
the 12.7s baseline — no regression from iters 200/203. Conclusion for
profiling: the dominant cost tracks **broken-link count × candidate-set
size** (the per-broken-link fuzzy pass), not corpus size. Target that,
and treat the no-prefix MDN run as the stress case. The snapshot index
buys only ~36% on `links` because bodies are still read.

## Findings (2026-08-26)

All numbers from a MacBook Pro (M-series), `cargo build --release`, scratch
GitHub-Docs-shaped corpora (961/960 files, `actions`/`graphql`/`get-started`/
`code-security` trees, ~12–14 links per file) generated by the script
recorded in `research/links-perf-profiling-206.md`. Two variants:

- **`hyalo-githubdocs`** (adversarial): every broken target unique per link
  (typo-style, 7,730 broken links).
- **`hyalo-githubdocs-real`** (realistic / MDN-stress-shaped): ~120 broken
  site-absolute targets reused across all pages (5,782 broken links) — models
  the no-site-prefix MDN run where every site-absolute link is broken and
  heavily repeated.

### Reproduction (task 1)

| command | corpus | baseline (main @ 380314d) | after fix |
|---|---|---|---|
| `links fix` (dry-run) | adversarial | 4.67 s | 3.14 s |
| `links auto` (dry-run) | adversarial | 0.05 s | 0.05 s |
| `links fix` (dry-run) | realistic | 4.84 s | **0.95 s** |
| `links auto` (dry-run) | realistic | 0.05 s | 0.05 s |

`links auto` is a non-factor on link-heavy docs corpora (its cost is body
scanning for title mentions, which stays ~linear). `links fix` is the target,
confirming the rescope's "broken-link count × candidate-set size" conclusion.

### Profiling (task 2)

macOS `sample` on a debug-symbols build of the new
`cargo run -p hyalo-core --example links-perf` phase-timing harness
(discover 7.7 ms → index 41 ms → detect 110 ms → matcher 0.5 ms →
**plan_fixes 4.16 s**): ~87% of all samples inside `strsim::jaro_winkler`
under `LinkMatcher::find_match` — the fuzzy-candidacy gate called
O(broken × vault-size) times, once per broken link per file.

### iter-200 contribution (task 3)

Not `git stash`-comparable post-hoc; from the iter-206 profile the
site-prefix stripping in `find_match` and the round-trip guard are outside
the hot leaf entirely (the guard runs per *fix*, 7.5k times; the gate ran
7.4M times). iter-200's changes did not cause the 12.7 s figure.

### Fix (task 4) — landed

`LinkMatcher` now precomputes per-file filename stems at build time and
caches the threshold-gated fuzzy candidate **shortlist per distinct target
stem** (`fuzzy_shortlists`, lazily via `RefCell<HashMap<…, Rc<Vec<usize>>>>`).
The Jaro-Winkler full-vault gate runs once per distinct target stem instead
of once per broken link; per-link self-link filtering and
`candidate_confidence` ranking over the shortlist are unchanged (results are
byte-identical — see the two new `matcher_shortlist_cache_*` unit tests).
Complexity O(broken × vault) → O(distinct-stems × vault + broken ×
shortlist). Worst case (all-unique targets) still improves ~33% from the
stem precompute + smaller inner loop; realistic corpora improve ~5×.

### Regression guard (task 5)

- `xtask bench-scale` (iter-224) already times `links fix` on a 14k-file
  vault: median 1.43 s vs 15 s budget — passing with an order of magnitude
  of headroom, so no new threshold was added.
- The `links-perf` example is committed so future regressions can be
  re-attributed to a phase in one command instead of rebuilding profiling
  tooling.
- Dogfood note: re-check `links fix` on GitHub Docs / MDN at the next
  pre-release dogfood ([[dogfood-results/dogfood-v0210-pre2-integrity-wave]] convention).
